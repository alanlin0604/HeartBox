## 1. 專案是什麼

**一句話：** HeartBox 心事盒是一款結合 AI 情緒分析、長期心情統計與本地化心理諮商資源的「個人心靈日記」App，網頁版加上 iOS app 雙端共用同一套後端。

**它解決什麼問題：**
- 一般人寫日記只能「記錄」，沒有人幫你看出規律。HeartBox 用 AI 幫你**讀出長期情緒模式**（例如：你週末比平日低落、6 月對你來說特別重）。
- 心理諮商門檻高、貴、難約。HeartBox 提供日常的**「軟性照顧」**作為前置 — 真的需要專業時也內建諮商師媒合。
- 市面上類似 app 多半把日記上傳到第三方 AI（ChatGPT / Gemini），有隱私風險。我們**自建 LLM**，所有日記內容不離開我們的伺服器。

**主要使用者：**
- 想自我覺察、但不想找專業諮商的一般人
- 大學生、年輕上班族（主要在台灣）
- 已經有諮商習慣、想記錄日常情緒給諮商師看的人

### 一張圖看不懂？文字版的「一筆日記的旅程」

1. **使用者** 在網頁/手機上寫一篇日記，按下「儲存」
2. 內容透過 HTTPS 傳到 `api.heartbox.tw`（其實是 Cloud Run 的 Django）
3. Django 收到請求後：
   - 用 JWT token 確認使用者身分
   - 把日記內容用 **AES-128 加密** 後存進 Postgres
   - 同時拋一個 **背景任務** 給 AI 分析（不阻塞使用者）
4. 使用者立刻看到日記出現在列表，**前端 UI 不用等 AI**
5. 背景：Django 呼叫 `llm.heartbox.tw`（其實是你家裡的 TAIDE 模型）做情緒分析、產生暖心回饋
6. AI 結果回來後，透過 **WebSocket** 推播給前端
7. 前端在原本那篇日記上**自動補上**情緒分數、AI 回饋（不用重整頁面）

## 3. 技術棧（一表看完）

| 層 | 用什麼 | 為什麼選它 |

| **前端框架** | React 18 + Vite | React 是業界標配；Vite 比 webpack 快 10 倍 |
| **樣式** | Tailwind CSS 4 | Utility-first，不用寫 CSS 檔，UI 改起來快 |

| **iOS App** | Capacitor 7 | 把 React App 包成原生 iOS，比 RN 簡單 |
| **PWA** | Service Worker (手刻) | 離線時也能讀已寫日記、預載 shell |
| **後端框架** | Django 5 + DRF | 自帶 admin、ORM、認證；DRF 寫 API 很快 |
| **資料庫** | Postgres 16 (Neon) | Serverless、自動 scale、TLS 連線 |
| **任務佇列** | Celery + Upstash Redis | 背景跑 AI 分析、推播、報告產生 |

| **向量檢索** | ChromaDB + bge-m3 embedding | 心理知識庫的 RAG（問問題時找相關資料） |
| **加密** | Cryptography (Fernet AES-128) | 業界標準，比自己刻 RSA 安全 |
| **認證** | JWT + 2FA (TOTP) | Stateless、好擴展；2FA 用 Google Authenticator |
| **檔案儲存** | Google Cloud Storage | 日記附圖、頭像、PDF 匯出 |
| **錯誤追蹤** | Sentry | 自動回報前端崩潰 + 後端 exception |
| **部署** | Cloud Run + Cloudflare Pages | 後端容器化、前端 CDN 邊緣 |
| **CI/CD** | GitHub Actions | 推到 main 自動 build + deploy |
| **本機 LLM 守護** | NSSM (Windows Service) | 重開機後 LLM 自動啟動，不用人工 |
| **本機 LLM 對外** | Cloudflare Tunnel | 不開外部 port，更安全 |

## 4. 前端是怎麼運作的

### 4-1 為什麼選 React

- **元件化** — 一個 `<NoteCard />` 元件可以重複用在日誌列表、搜尋結果、詳情頁，不用複製貼上
- **單向資料流** — bug 容易追，狀態變了畫面就更新
- **生態大** — Tiptap、Recharts、Tailwind 都有對應 React 套件
- **React 18 的並行渲染** — 大列表渲染不卡頓

### 4-2 Vite 加速

- **冷啟動 < 1 秒**，相比之下 webpack 要 30 秒以上
- **HMR (Hot Module Replacement)** — 改一個檔案，瀏覽器立刻看到變化，不用 reload
- **Build 後輸出靜態檔**，可丟到 Cloudflare Pages CDN

### 4-3 樣式：Tailwind 4

- 不寫 CSS 檔，直接在 JSX 標記 `className="text-sm font-bold text-orange-500"`
- 大型 codebase 維護成本低 — 沒有「全域 CSS 衝突」問題
- 配合 **CSS 變數** 做主題：`--color-primary`、`--text-secondary` → 暗黑/明亮模式一鍵切換

### 4-4 i18n 多語

我自己刻的輕量版 `t()`：

```javascript
const t = useCallback((key, vars) => {
  let text = translations[lang]?.[key] || translations.en?.[key] || key
  if (vars) Object.entries(vars).forEach(([k, v]) => {
    text = text.replaceAll(`{${k}}`, v)
  })
  return text
}, [lang])
```

- **3 個 locale 檔**（zh-TW / en / ja），每個 1981 個 key
- `t('dashboard.title')` 自動回傳當前語言的字串
- 支援變數代入：`t('login.warmingUpElapsed', { seconds: 12 })` → "已等待 12 秒…"
- 用 `replaceAll` 確保同 key 出現多次時都被代入（之前的 bug）

### 4-5 PWA + Service Worker

- 寫了 `frontend/public/sw.js` 自己管 cache
- 離線時：showing offline shell + 已 cache 的 GET 結果
- 部署版本變化會塞進 sw.js 註解，瀏覽器偵測到新版本會在「使用者非聚焦時」reload（不會打斷打字）

### 4-6 iOS App (Capacitor)

- 同一份 React code，用 `npx cap copy` 包進 Capacitor 容器
- 透過 `window.Capacitor.isNativePlatform()` 偵測，網頁版隱藏「Apple Health 整合」等手機限定功能
- 推播用 Apple Push Notification Service (APNs)，後端用 `apns2` 套件

### 4-7 路由與頁面

- 用 `react-router-dom` 7
- 主要頁面：
  - `/` 日誌
  - `/login`, `/register`
  - `/dashboard` 統計 dashboard
  - `/community` 社群
  - `/counselors` 諮商師列表
  - `/admin` 管理員面板
  - `/settings` 設定
- **保護路由** — `<ProtectedRoute>` 未登入直接 redirect 到 `/login`
- **管理員路由** — 額外檢查 `user.is_staff`

## 5. 後端是怎麼運作的

### 5-1 Django + DRF 的角色

- **Django** 是後端框架，提供 ORM（不用寫 SQL）、admin 介面（管理用）、認證系統
- **DRF (Django REST Framework)** 是建立 REST API 的工具，自動處理 JSON 序列化、權限、分頁、過濾

我們有 **136 個 API endpoint**，分散在：
- 認證 (`/api/auth/*`)：登入、註冊、refresh、2FA、Google OAuth、忘記密碼
- 日記 (`/api/notes/*`)：CRUD、批次刪除、垃圾桶、回收、附件上傳
- 分析 (`/api/analytics/*`)：心情趨勢、相關性、insights、calendar
- 社群 (`/api/community/*`)：公開貼文、按讚、留言、檢舉
- 諮商 (`/api/counselors/*`)：列表、預約、評論
- 管理 (`/api/admin/*`)：用戶管理、回饋、稽核、ML 監控
- 健康 (`/api/health/*`)：步數、心率、HRV、睡眠（從 Apple Health 來）
- AI 對話 (`/api/ai-chat/*`)：跟 TAIDE 對話的 session 管理

### 5-2 資料庫：Postgres 16 on Neon

**為什麼選 Postgres：**
- 業界最強的 open-source 關聯式資料庫
- 支援 JSONB（彈性欄位）、全文檢索、CTE、地理資料、時序資料
- 比 MySQL 在複雜查詢上強很多

**為什麼選 Neon：**
- Serverless — 沒人用時自動縮到零，省錢
- 連線走 TLS — 從 Cloud Run 連過去全程加密
- 內建 branching — 之後可以切「測試分支 DB」做 staging

**有 47 個 model（表）：**
- `CustomUser` 使用者（含 2FA、家長同意、刪除排程）
- `MoodNote` 日記（**內容欄位加密**）
- `Tag` 標籤
- `NoteAttachment` 附件（圖片）
- `JournalStreak` 連續寫日記紀錄
- `HealthMetric` 健康指標
- `Conversation`, `Message` 諮商師與用戶對話
- `Booking`, `TimeSlot` 預約時段
- `PublicPost`, `Comment` 社群貼文
- `Notification` 通知
- `AuditLog` 管理員操作稽核
- `Feedback` 使用者回饋
- ... 等等共 47 個

### 5-3 背景任務：Celery + Redis

**為什麼需要背景任務？**

舉例：使用者按下「儲存日記」，如果同步等 AI 分析跑完，使用者要等 5-10 秒才看得到結果，體驗很差。

所以我們：
1. 立刻把日記存進 DB → 回應使用者 「已儲存」
2. **背景** 派出一個 Celery worker 去呼叫 LLM 做分析
3. 分析完用 WebSocket 推回前端

**Redis 的角色：**
- 訊息佇列（Celery 用）
- API rate limiting (DRF Throttling)
- Daily prompt cache（同一個使用者一天只生成一次 prompt）
- Personal-suggestion cache（每人每天每地區 12h cache）

### 5-4 排程任務：Cloud Scheduler

每天/每小時自動觸發：
- `cleanup_deleted_users` — 30 天前申請刪除的帳號真的硬刪
- `daily_streak_check` — 計算每個使用者的連續天數
- `send_daily_reminder` — 早上 9 點推播提醒
- `generate_weekly_summary` — 每週一產生上週總結

## 6. AI 是怎麼做的

### 6-1 三個 AI 模型分別做什麼

| 模型 | 大小 | 用途 |
|---|---|---|
| **TAIDE-LX-7B-Chat** | 7 億參數 | 主要對話 LLM — 情緒分析、AI 回饋、每日 prompt、心理諮詢對話、今日建議 |
| **LLaVA-v1.6-mistral-7b** | 7 億參數 | 視覺理解 — 使用者上傳日記附圖時，理解圖像並結合內容做分析 |
| **bge-m3** | 5.7 億參數 | 多語向量編碼 — 把心理知識文章變成「向量」，配合 RAG 找相關建議 |

### 6-2 為什麼自己跑而不用 OpenAI / Gemini？

**隱私是首要考量。** 心理日記是極度敏感的資料：
- ChatGPT API 預設會把對話拿來訓練模型（除非付額外費）
- 即使付費，資料仍經第三方公司
- 心理健康內容如果外洩，使用者可能受到歧視（保險、求職）

**TAIDE 的優勢：**
- 是**台灣國科會出品的繁中模型**，比 ChatGPT 對台灣語境更貼近（諺語、文化、用詞）
- 模型部署在我們本機 — 日記內容**從未離開我們的伺服器**
- 即使 OpenAI 漲價或關閉 API，我們也不受影響

**缺點：** 7B 參數比 GPT-4 (~1.7 兆) 小很多，所以：
- 比較慢（每次回應 5-15 秒）
- 偶爾品質不穩定
- 我們有 **template fallback 機制**：LLM 失敗時退回預先寫好的固定模板

### 6-3 一篇日記的 AI 分析流程

```
使用者按下「儲存」
   │
   ▼
Django views/notes.py::perform_create
   │
   ├──[1] 加密內容 + 存入 DB
   │
   ├──[2] 立即回應給前端 → 使用者看到日記出現
   │
   └──[3] 開背景執行緒 _run_full_analysis(note_id)
              │
              ▼
         呼叫 LLMProvider.chat(...)
              │
              ▼
         透過 httpx POST 到 llm.heartbox.tw/v1/chat/completions
              │
              ▼
         本機 FastAPI server（OpenAI 相容介面）
              │
              ▼
         TAIDE 模型推理（~5-10 秒）
              │
              ▼
         回傳：{ sentiment_score: 0.4, stress_index: 6, ai_feedback: "..." }
              │
              ▼
         Django 收到 → 更新 DB → 透過 WebSocket 通知前端
              │
              ▼
         前端在原本那篇日記上補上情緒分數 + AI 回饋
```

**錯誤處理（重要）：**
- LLM 超時（>60s）→ 用情緒詞典做粗略分析作為 fallback
- LLM 回傳異常 → 留空，使用者只看不到 AI 回饋，日記本身仍然儲存成功
- 整個鏈路有 5 層降級設計（remote_taide → mock_provider → 詞典 → 空字串），不會因為 LLM 掛掉導致日記無法儲存

### 6-4 個人化洞察是如何算出來的

`backend/api/services/analytics.py::get_personal_insights`

過去 180 天的日記資料 → 跑 **5 維度規律檢測**：

1. **月段偏好**（早 1-10 / 中 11-20 / 晚 21-月底）
   - 把所有日記按月段分組
   - 算每組的平均情緒
   - 如果 max-min 差 ≥ 0.3 且每組樣本 ≥ 3 → emit insight

2. **平日 vs 週末**
   - 0.2 差距以上才認定為「明顯」

3. **月份極值**
   - 找出最高/最低的月份，0.3 差距以上

4. **天氣 (晴 vs 雨)**
   - 配合日記的 metadata.weather

5. **溫度帶 (<20°C / 20-25 / >25)**

**重點：完全是統計演算，沒用 LLM。** 因為：
- 統計可解釋（評審問為什麼，可以指著數字解釋）
- 確定性高（同樣資料永遠得出同樣結論）
- 即時計算便宜（DB query + Python 比較）

### 6-5 「今日個人化建議」如何結合 LLM + 天氣 + 統計

```
1. 使用者打開日誌頁
   ↓
2. 前端取得瀏覽器定位 → POST /api/personal-suggestion/ { lat, lon }
   ↓
3. Django 收到後：
   ├─ 從 DB 抓 personal_insights （上一節算好的）
   ├─ 呼叫 Open-Meteo 抓今天該位置的天氣
   ├─ 計算今天命中哪些觸發條件（e.g.「今天是週末，你過去週末心情較低」）
   └─ 把以上資料組合成 prompt 餵給 TAIDE
       ↓
4. TAIDE 寫一段 2-3 句的暖心建議
   ↓
5. Redis 快取 12 小時（每人每天每地區只生成一次）
   ↓
6. 前端顯示這段話
```

**3 層 fallback：**
1. **首選**：TAIDE 寫的客製段落
2. **退回 #1**：如果 TAIDE 掛掉，前端用統一模板組合（依命中的條件填詞）
3. **退回 #2**：如果連命中條件都沒有（新用戶），顯示「繼續寫日記，個人化建議會慢慢出現」

## 7. 安全性（用最白話的方式）

> 評審如果問安全性，這節是重點。

### 7-1 加密（最重要）

#### 比喻：保險箱 + 鑰匙

想像 DB 是一間倉庫，每個日記是倉庫裡的一個箱子：
- **不加密** = 箱子上印著日記內容，任何走進倉庫的人（DBA、駭客、洩漏的 DB dump）都讀得到
- **加密** = 箱子上是亂碼，只有我們的伺服器有鑰匙能讀

#### 具體用什麼

**Fernet (AES-128-CBC + HMAC-SHA256)**
- 業界標準 — Python `cryptography` 套件提供
- **AES-128**：對稱加密演算法。需要 128-bit 的金鑰才能解
- **HMAC-SHA256**：附加的「印章」防止資料被竄改

#### 哪些資料被加密

```
✅ 日記內容 (MoodNote.encrypted_content)
✅ AI 回饋 (MoodNote.ai_feedback)         ← Phase 0b 新加
✅ 2FA 密鑰 (CustomUser.totp_secret)      ← Phase 0b 新加
✅ 通知內容 (Notification.body)           ← Phase 0b 新加
✅ 私訊內容 (Message.content)             ← Phase 0b 新加
✅ AI 對話訊息 (AIChatMessage.content)    ← Phase 0b 新加
✅ 健康指標 (HealthMetric.value)          ← Phase 0b 新加
```

#### 哪些「故意」沒加密

- 使用者名稱、email（要登入用）
- 標籤名稱（要做統計、要 GROUP BY）
- 日記的情緒分數、時間戳（要畫圖表）
- 公開社群貼文（用戶刻意要分享給其他人看）

**為什麼這樣切？** 加密的欄位是「**只有本人會看的**」；沒加密的是「**統計上要做聚合的**」。如果情緒分數加密，後端就無法畫趨勢圖。

#### 金鑰怎麼管

- 金鑰存在 Cloud Run 的環境變數 `ENCRYPTION_KEY`（base64 編碼的 32 bytes）
- 程式碼中**從未寫死金鑰**（git 不會洩漏）
- 金鑰輪換流程：產生新金鑰 → 把所有 row 用新 key 重加密 → 切換主 key（已實作在 `reencrypt_notes.py`）

#### 為什麼這很重要

**假設 Neon Postgres 被駭客整個拖庫：**
- ❌ 沒加密：所有人的日記直接洩漏 → 心理隱私大爆炸
- ✅ 有加密：駭客看到的是隨機亂碼，沒有 `ENCRYPTION_KEY` 解不開

這就是「**分層防禦 (Defense in Depth)**」— 即使一道防線破了，下一道還在。

### 7-2 認證與授權

#### 為什麼用 JWT 不是傳統 session？

- **傳統 session**：伺服器要記住「token X 對應 user Y」 → 多台伺服器要共享 session → 麻煩
- **JWT**：token 本身就包含資訊（signed），伺服器**不用記住**，驗簽就好 → 容易擴展

#### Access Token + Refresh Token

```
登入時 → 拿到 2 個 token：
   - access_token （效期 15 分鐘）
   - refresh_token（效期 30 天）

呼叫 API 時 → 帶 access_token

access_token 過期 → 用 refresh_token 換新的（不用重新登入）

refresh_token 過期 → 重新登入
```

**好處：** 即使 access_token 被偷，15 分鐘就失效；refresh_token 只在登入時傳輸一次。

#### 2FA (兩步驟驗證)

啟用後流程：
1. 使用者掃描 QR code 加入 Google Authenticator
2. 登入時：輸入帳密 + 6 位數動態碼
3. 動態碼用 **TOTP 演算法**（time-based one-time password），每 30 秒換一次

我們還做了：
- **備援 codes** — 萬一手機掉了，可以用備援碼登入
- **TOTP secret 加密儲存** — 即使 DB 洩漏，也無法產生動態碼

#### 帳號鎖定

連續輸錯密碼 → 鎖帳號：
- 5 次錯 → 鎖 15 分鐘
- 防 brute force 攻擊

實作：`CustomUser.failed_login_count` + `locked_until`，每次登入 view 檢查。

### 7-3 防護機制

#### CSP (Content Security Policy)

`frontend/public/_headers` 設定：
```
Content-Security-Policy: default-src 'self';
  script-src 'self' https://accounts.google.com;
  style-src 'self' 'unsafe-inline' https://fonts.googleapis.com https://accounts.google.com;
  img-src 'self' data: blob: https://storage.googleapis.com https://heartbox.tw https://api.heartbox.tw;
  connect-src 'self' https://api.heartbox.tw wss://api.heartbox.tw https://accounts.google.com https://api.open-meteo.com;
  frame-ancestors 'none';
  ...
```

**用白話講**：瀏覽器只允許網頁從**白名單**的網址抓資源。即使駭客成功插入惡意 `<script src="evil.com">`，瀏覽器會擋掉。**防 XSS 最後一道防線。**

#### HSTS (HTTP Strict Transport Security)

`Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`

告訴瀏覽器：「未來 2 年內只用 HTTPS 連我」。防止 SSL 降級攻擊。

#### CORS

只允許 `heartbox.tw`、`www.heartbox.tw` 呼叫 API，別人網站想偷打 API 會被擋。

#### Rate Limiting

DRF 內建的 throttle：
- 匿名用戶：60 req/min
- 已登入：1000 req/min
- 登入 endpoint：100 req/hour（防爆破）

#### RBAC (角色權限)

3 種角色：
- 一般用戶 (`is_active=True`)
- 諮商師 (`is_counselor=True`，有 CounselorProfile)
- 管理員 (`is_staff=True`，超級管理員 `is_superuser=True`)

每個 API view 用 `permission_classes = [IsAdminUser]` 之類的明確限制。

#### Audit Log

所有「敏感操作」都會記錄：
- 管理員修改用戶 staff 狀態
- 諮商師審核通過/拒絕
- 帳號刪除請求

存在 `AuditLog` 表，**只能 append，不能改也不能刪**（程式碼層面確保）。

### 7-4 隱私與合規

#### 台灣個資法 (PDPA) 合規

- 註冊時必須勾選「同意蒐集個資」+ 「同意隱私政策」
- 蒐集的時間戳 + 版本都存進 DB（之後法律訴訟可舉證）

#### GDPR (歐盟個資法) 友善設計

雖然我們主要服務台灣，但也照 GDPR 標準：
- **可下載自己的所有資料**（`/api/export-data/`，匯出 JSON + 附件 ZIP）
- **可刪除帳號**（30 天緩衝期內可撤回，30 天後 Cron 真的硬刪）
- **AI 訓練用同意是獨立勾選** — 即使註冊也可以不同意 AI 訓練

#### 13-17 歲家長同意機制

- 註冊時要勾選年齡帶（18+ / 13-17 / under 13）
- under 13 直接拒絕註冊（法律不允許）
- 13-17 要填家長 email → 系統寄信給家長確認 → 家長點連結同意才解鎖帳號

#### 30 天刪除緩衝

使用者按「刪除帳號」：
1. `CustomUser.deletion_scheduled_at = now + 30天`
2. 帳號變不能登入，但資料還在 DB
3. 30 天內可寄信給 support 撤回
4. 30 天後 Celery beat 任務真的執行 `user.delete()`（cascade 刪除所有相關資料）

## 8. 部署與運維

### 8-1 Cloud Run

**為什麼：** Google 的 serverless 容器平台
- 沒人用時自動縮到 0 instance → 省錢
- 突然湧入用戶時自動 scale up
- 自動 HTTPS + CDN
- 直接 `gcloud run deploy --source=./backend` 就完成 build + deploy

**配置：**
- Region: `asia-east1`（台北）
- Memory: 4 GiB（為了載 LLM 客戶端 + ML 模型）
- Max instances: 100
- Min instances: 0（省錢，但首次請求會有 cold start ~10-30 秒）

### 8-2 Cloudflare Pages

**為什麼：** 免費的靜態網站 CDN
- 全球 200+ 邊緣節點
- 自動 HTTPS
- 推到 GitHub → 自動 build + deploy

**前端路徑：**
1. 推 commit 到 `main` 分支
2. GitHub Actions 觸發
3. Cloudflare Pages 跑 `npm run build`
4. 輸出靜態檔上傳到 CDN
5. 2-3 分鐘後全球生效

### 8-3 Cloudflare Tunnel (LLM 對外)

**問題：** LLM 模型跑在 alan 家的電腦上，但雲端的 Cloud Run 怎麼連到家裡電腦？

**解法：** Cloudflare Tunnel
- alan 家電腦跑一個 `cloudflared` daemon
- 它主動跟 Cloudflare 建立**長連接**（不用開 port、不用 DDNS）
- `llm.heartbox.tw` 的請求 → Cloudflare → 透過 tunnel → 你家電腦的 8765 port
- 加上 API key 驗證，外人打不進來

**為什麼這樣設計：**
- 不需要靜態 IP
- 不用設定路由器 port forwarding
- 自動 HTTPS（憑證 Cloudflare 管理）
- 防 DDoS（Cloudflare 邊緣擋掉）

### 8-4 NSSM (Windows Service)

**問題：** LLM server 是 Python script，alan 重開機後不會自動啟動。

**解法：** NSSM (Non-Sucking Service Manager)
- 把 `python -m llm_server` 註冊成 Windows Service
- 開機自動啟動
- 萬一掛掉自動 restart（5 秒後）
- log rotation（每天一個 log 檔，保留 7 天）

### 8-5 監控

#### Sentry (錯誤追蹤)
- 前端 / 後端 exception 自動上報
- 含 stack trace + 用戶操作軌跡
- 重大錯誤會發 email 通知

#### Cloud Run 內建 metrics
- Request count, latency, error rate
- Memory / CPU usage
- Cold start frequency

#### llm_server log
- 每次 LLM 呼叫的 latency
- Token usage（input + output）
- Error rate

## 9. 主要功能技術細節

### 9-1 日記功能

- **富文本編輯器** (Tiptap)：粗體、斜體、列表、引用、復原/重做
- **語音輸入** (Web Speech API)：點麥克風直接說話轉文字

- **標籤管理**：可以建立彩色標籤，搜尋按標籤過濾
- **活動追蹤**：選今天做了什麼活動（運動、社交、閱讀…）
- **天氣與溫度**：寫日記時可手動標記，做心情×天氣分析
- **匯出 PDF**：把選定日記匯出成 PDF（給諮商師看）

### 9-2 情緒分析

LLM 跑完後產生 3 個指標：
- `sentiment_score`：-1 到 +1（負向到正向）
- `stress_index`：0 到 10（無壓力到極度壓力）
- `ai_feedback`：一段 2-3 句的暖心話

**Prompt 工程**：我們的 system prompt 經過多次調整，確保：
- 回應「貼近朋友語氣」而非「諮商師說教」
- 避免「根據資料顯示...」這種冷冰冰句型
- 控制長度（60-120 字）
- 中文標點正確（不混半形/全形）

### 9-3 個人化洞察

5 維度的統計檢測（已在 §6-4 詳述）。

額外的設計細節：
- **嚴重程度**：差距大 → "strong"（橘色強調）；差距小 → "mild"（灰色低調）
- **樣本數要求**：每組至少 3 筆，避免「2 筆雨天平均」這種統計噪音

### 9-4 今日建議

已在 §6-5 詳述。額外：
- 瀏覽器定位失敗時 → 退台北座標（HeartBox 主要 TW 用戶）
- 用戶第一次會跳定位授權框 → 拒絕也沒關係，會 cache 24h
- LLM 呼叫成功時 cache 12h；失敗時 cache 10 分鐘（避免長時間鎖死壞 cache）

### 9-5 健康整合（Apple Health）

- iOS app 透過 Capacitor 的 `@capacitor-community/healthkit` 套件
- 同步：步數、心率、HRV、活動卡路里、運動分鐘、睡眠
- 後端做相關性分析：「步數低於 6000 步的日子，平均心情比高於 8000 步的日子低 0.15 分」

### 9-6 社群

- 用戶可發匿名公開貼文
- 按讚、留言、檢舉
- 自動關鍵字審核（自殘/自殺字眼會觸發 crisis banner，顯示求助專線）
- 管理員審核檢舉，可下架貼文

### 9-7 諮商師媒合

- 諮商師申請流程：填執照號碼 → 管理員審核 → 通過後上架
- 用戶可看諮商師專長、評價、可預約時段
- 預約時段 + 線上 Conversation 對話
- 預約取消、評論機制

### 9-8 訂閱與週報

- 每週一自動產生「上週情緒回顧」
- 內容：心情趨勢、最頻繁的標籤、最低/最高日子的日記
- 用戶可設定是否接收 email 通知

### 9-9 危機處理

關鍵字偵測：
- 日記內容含「想死、自殺、自殘」等 → 自動 flag `crisis_detected: true`
- 前端收到後跳出 banner：「你並不孤單，這裡可以求助 → [1995 生命線]」
- 不會封鎖內容，但提示資源
- 同樣機制應用在 AI chat 對話

## 11. 評審可能會問的問題 (FAQ)

### Q: 為什麼選 TAIDE 不是 ChatGPT？

**A:** 三個理由：
1. **隱私** — 心理日記是極敏感資料，丟給 OpenAI 等於相信對方不會誤用。我們自己跑，資料不離開伺服器
2. **本地化** — TAIDE 是台灣國科會出品的繁中模型，對台語、台灣文化、本地語境更熟悉
3. **成本控制** — 用 ChatGPT 每千 token 都要錢，使用者越多越貴；自己跑只有一次性硬體成本

但我們也設計了「provider 抽象層」 — 萬一未來要切換到 ChatGPT 或 Claude，只要改一個 setting，程式碼不用大改。

---

### Q: 為什麼日記要加密？怎麼確保隱私？

**A:** 心理日記如果洩漏，後果嚴重（保險拒保、求職歧視、人際關係）。我們的多層保護：
1. **傳輸層**：HTTPS + HSTS + CORS
2. **儲存層**：欄位加密（AES-128）— 即使 DB dump 外洩，內容是亂碼
3. **存取層**：JWT + 2FA + 帳號鎖定
4. **應用層**：所有敏感操作有 audit log

即使駭客攻破其中一層，下一層還在防守。

---

### Q: 萬一 LLM 服務掛了怎麼辦？

**A:** 我們有 5 層 fallback：
1. 首選：TAIDE 本機推理
2. 退 1：超時 / 異常 → 改用詞典做粗略情緒分析
3. 退 2：詞典也失敗 → 留空 AI 回饋，日記本身仍然儲存
4. 退 3：每日建議 widget 改顯示模板 tips（不需 LLM）
5. 退 4：所有狀況都掛 → 使用者可以正常寫/讀日記，只是看不到 AI 功能

**核心原則：LLM 是「錦上添花」，不是「核心相依」。**

---

### Q: 怎麼處理使用者要求刪除資料？

**A:** GDPR + PDPA 標準流程：
1. 設定頁有「刪除帳號」按鈕
2. 點下去 → 30 天緩衝期（可撤回）
3. 30 天後 Celery cron 任務真的執行 `user.delete()`
4. 由於 Django ORM cascade，所有相關資料（日記、附件、標籤、預約、訊息）都一起刪
5. GCS 上的附件也會被 cleanup task 刪除

**另外，使用者也可以「下載我的全部資料」**（GDPR Right to Data Portability），匯出 JSON + 圖片 ZIP。

---

### Q: 怎麼擴展到 10 萬使用者？

**A:** 目前架構已經設計成可水平擴展：
- **Cloud Run** auto-scale 到 max 100 instances
- **Neon Postgres** serverless，自動 scale compute
- **靜態前端**走 Cloudflare CDN，無上限
- **背景任務**走 Celery，可以加 worker

實際瓶頸會是：
1. **LLM 推理** — 7B 模型在一台機器上 throughput 有限。對策：可以加 GPU 機器、或 fallback 到 ChatGPT
2. **資料庫寫入** — Postgres 寫入有上限。對策：sharding by user_id

但這些都是「10 萬用戶以上才會碰到」的問題，目前架構足以支撐到萬人級。

---

### Q: 部署成本大概多少？

**A:** 目前狀態（含 260 個 seed users）：
- Cloud Run: ~$5/月（serverless，幾乎不收費直到爆量）
- Neon Postgres: $0（免費 tier 足夠 10GB 以內）
- Cloudflare Pages: $0（前 500 build/月免費）
- Sentry: $0（免費 tier 5K events/月）
- 本機 LLM 電費: ~NT$300/月
- Domain: NT$300/年（heartbox.tw）

**總計：每月不到 NT$500。** 這是因為大量用了免費/serverless 服務，沒有固定 server 成本。

---

### Q: AI 回答如果說錯怎麼辦？

**A:** 三層防護：
1. **提示工程** — system prompt 嚴格指示「不要給醫療建議」「不要診斷」
2. **輸出 sanitize** — 後端有 `scrub_llm_output()` 過濾敏感 token、prompt template 洩漏
3. **危機字眼偵測** — LLM 回答含自殘/自殺字眼會被 flag，前端跳危機資源

加上免責聲明：app 內明確標示「AI 回饋僅供參考，不取代專業醫療」。

---

### Q: 為什麼有 5326 → 3877 這種變動？是不是不穩定？

**A:** 那是我們 reseed 測試資料時改變了起始日期（從 2 月改成 4 月）以符合「user testing 從 4 月開始」的時間軸。Production seed 是 idempotent + 有清晰的 marker，demo 結束後一個指令就清乾淨。

---

### Q: 如果 demo 當天 Cloud Run cold start 卡 30 秒怎麼辦？

**A:** 三招：
1. **Demo 前 1 分鐘先 ping 一次** `/healthz` 暖機
2. **LoginPage 已有進度條** 顯示「正在喚醒伺服器，已等待 X 秒…」 — 不會看起來像當機
3. **全域 429/503 retry** — 即使 cold start 期間有些請求 503，前端會自動重試 2 次
